# Кварта — лендинг обжарки кофе

Лендинг для вымышленной минской обжарки «Кварта» по тестовому заданию
(бриф: `analysis/kvarta-brief.pdf`). Цель сайта — заявка на подписку
или разовый заказ через форму; корзины и онлайн-оплаты нет.

**Стек:** Next.js 16.4.2 (App Router, TypeScript, Tailwind), деплой — **Vercel**.
Приложение лежит в `kvarta-web/`.

## Архитектура: полностью SSG + один эндпоинт

Страница генерируется статически при сборке. Вся интерактивность —
один клиентский остров (форма) и `POST /api/lead`.

Почему не «статический сайт без сервера вообще»: бриф требует серверную
логику — валидацию белорусского номера, дедупликацию повторных заявок
в течение 10 минут и видимую человеку ошибку при неудачной отправке.
Чистая статика этого не даёт. Что сделано статикой: все секции, тексты,
цены — HTML поставляется без ожидания JS.

Почему `fetch` + отдельный эндпоинт, а не Server Action:

- в брифе прямо сказано «эндпоинт, например `POST /api/lead`» — его
  можно проверить curl-ом независимо от страницы;
- эндпоинт дёргают не только страницы сайта, но и внешние источники
  (реклама, менеджер) — нужен явный JSON-контракт, а не внутренний
  механизм фреймворка;
- attribution (utm/referrer) приходит в теле запроса и должен
  переживать любую доставку.

Стоимость: App Router всё равно тянет react-рантайм в браузер
(~176 KB gzip на страницу — замерено на дефолтном шаблоне), поэтому
клиентский остров формы добавляет к этому ~1–3 KB. Основные риски
по Lighthouse mobile — шрифты и фото, не JS.

## Дизайн-решения (locked)

Полный журнал — `design-tokens.md`. Кратко:

- **Шрифты:** Unbounded (дисплей/цены) + Onest (текст/UI), третьих нет.
  Рукописные отклонены (Caveat и др.) — бриф «тёплый и простой, без
  пафоса и без „премиального“ глянца».
- **Палитра:** кремовый фон `#F7F3EA`, тёмно-коричневый текст `#221B14`,
  единственный яркий акцент — жжёный оранжевый `#C05621` (CTA/цены),
  honey `#D99A2B` только на тёмных секциях. Красный `#ef5619/#d12328`
  намеренно не используется — он у половины референсов
  (см. `analysis/analysis.md`).
- **Ритм страницы:** тёмный герой (espresso) → светлая середина →
  одна тёмная секция подписки → тёмный футер.
- Контрасты всех пар проверены по WCAG AA/AAA — таблица
  в `design-tokens.md`.
- Превью цветов: `color-mock.html` (живой A/B: акцент и герой).

## Хранение заявок: почему SQLite, а не файл

Рассматривали два варианта: JSONL-файл и база.

**Файл (JSONL)** — нулевой сетап, разрешён брифом («Куда складывать
заявки — выберите сами: файл, SQLite или что-то ещё»). Отклонили: на
Vercel у инстанса нет постоянного диска — записываемый `/tmp` умирает
при холодном старте и не общ между инстансами. Заявка с рекламы
теряется до того, как её увидит менеджер; дедупликация повторов в
течение 10 минут тоже не переживает рестарт.

**БД (SQLite)** — данные лежат вне инстанса и переживают рестарты.
Дедупликация живёт в самой таблице: вставка
`INSERT … WHERE NOT EXISTS (телефон AND created_at > now−10 мин)` в
одной транзакции; строки не вставилось → дубль → отвечаем «принято»
без второй записи.

Как SQL-движок берём **Turso** — облачный SQLite: подключение по
`DATABASE_URL` и `DATABASE_AUTH_TOKEN`, клиент `@libsql/client`,
одни и те же запросы локально и в проде.

Отчёт по источникам — команда `npm run leads` (CLI-скрипт в репозитории;
публичного GET-эндпоинта нет, чтобы не светить заявки).

## Допущения

- **Защита эндпоинта:** список разрешённых доменов читается из
  `ALLOWED_ORIGINS` в `.env` (не хардкодится), проверяется
  `Origin`/`Referer`, обязателен `Content-Type: application/json`,
  есть honeypot-поле. Это отсекает наивный спам; от продвинутых ботов
  не защищает — сознательный компромисс: аудитория идёт из рекламного
  трафика, CAPTCHA стоит конверсии.
- **Attribution:** utm-метки и referrer берутся из query страницы
  на клиенте и складываются в тело заявки — бриф требует, чтобы
  менеджер знал, откуда пришёл клиент.

Поля атрибуции в заявке (хранятся в одной JSON-колонке `origin`):

| Поле | Значение | Пример |
|---|---|---|
| `source` | откуда трафик | `instagram`, `google` |
| `medium` | тип канала | `cpc`, `social`, `email` |
| `campaign` | кампания | `winter-sub` |
| `content` | вариант креатива (A/B) | `video`, `photo-1kg` |
| `term` | ключевое слово из поисковой рекламы | `кофе подписка` |
| `page` | URL, на котором открыта форма (обязателен) | `https://…/?utm_source=…` |
| `referrer` | внешняя страница-источник, если utm нет | `https://t.me/…` |

## Структура репозитория

- `kvarta-web/` — Next.js-приложение (сайт, эндпоинт)
- `design-tokens.md` — журнал дизайн-решений (шрифты, цвета, ритм)
- `analysis/` — разбор 16 референсов (`analysis.md`, `links.md`) + бриф (PDF)
- `color-mock.html`, `font-expiriments/` — полочные образцы решений

## Запуск

```bash
cd kvarta-web
cp .env.example .env.local   # заполнить: DATABASE_URL, DATABASE_AUTH_TOKEN, ALLOWED_ORIGINS
npm install
npm run dev                   # http://localhost:3000
npm run build                 # проверка статической сборки
```

Для проверки эндпоинта локально (валидная заявка; `origin.page`
обязателен — из него менеджер видит, откуда пришёл клиент):

```bash
curl -X POST http://localhost:3000/api/lead \
  -H "Content-Type: application/json" \
  -H "Origin: http://localhost:3000" \
  -d '{"name":"Тест","phone":"+375291234567","interest":"subscription","consent":true,"origin":{"page":"http://localhost:3000/"}}'
```

Ответы: `200` — принято (в т.ч. дубль за 10 минут), `400` — ошибка
поля (в `field` — какое), `403` — домен не в `ALLOWED_ORIGINS`,
`503` — не заданы переменные окружения (подробности — в логах сервера).

Отчёт по заявкам (нужен заполненный `DATABASE_URL`):

```bash
npm run leads                          # все заявки, сгруппированы по источнику
npm run leads instagram                # только источник instagram
npm run leads instagram winter-sub     # источник + кампания
```
